# HTTP 特性整理

## 五层模型

- 应用层：HTTP, FTP, DNS（具体应用）

- 传输层：TCP, UDP（消息的可靠传递）

- 网络层：IP, 路由器（在互联网中找到对方）

- 数据链路层：MAC, 交换机（在子网中找到对方）

- 物理层：电缆（如何用信号表示）

在网络通信中，数据依次经过每一层的处理，发出的时候**封装**，接收的时候**解封装**

## URL 的定义

URL 即统一资源定位符

标准 http 的 URL 构成：`{schema}://{domain}:{port}:{query}#{hash}`

## HTTP 请求的构成

- 请求行 Line：包含请求方法、请求路径、版本号

- 请求头 Header：请求头部信息，例如 Content-Type

- 请求体 Body：传输的数据（类型需要跟服务端约定）

## 响应状态码

### 1xx：收到请求，需要继续执行

100 临时响应，可以继续请求

101 根据客户端请求切换协议，例如 websocket 或 http2

### 2xx：请求成功

200 成功

201 已创建

202 已接收请求，尚未处理

203 返回的信息来自另一个来源

204 无返回内容

205 重置内容

206 成功处理了部分请求

### 3xx：重定向或缓存

300 多种选择

301 永久重定向

302 临时重定向

303 查看其它位置

304 资源未发生变更，通知客户端可以使用缓存

305 使用代理

### 4xx：请求错误

400 错误的请求，服务器不理解

401 要求进行身份验证

403 拒绝请求

404 未找到请求的资源

405 禁止使用此方法

406 不接受响应的资源

407 需要代理授权

408 请求超时

### 5xx：服务器错误

500 服务器内部错误

501 不具备完成请求的功能

502 错误的网关

503 服务不可用（超载或停机维护）

504 网关超时

505 不支持的 http 版本

## 版本

到目前为止，HTTP 常⻅到版本有 HTTP/1.0，HTTP/1.1，HTTP/2.0，HTTP/3.0，不同版本的 HTTP 特性 是不一样的。

### HTTP 0.9

1. 支持 GET

2. 没有请求头

3. 只能返回 HTML 字符串

4. 服务端响应后立即关闭 TCP

### HTTP 1.0

1. 新增 POST、HEAD 方法

2. 加入请求头和响应头

3. 请求行加入版本号标识

4. 支持传输数据格式：图片、音视频、二进制

### HTTP 1.1（主流）

1. 支持长连接

HTTP/1.1 默认使用持久连接，除非通过 `Connection: close` 等方式关闭；不需要靠 `Connection: keep-alive` 才开启。

2. 管道化传输

客户端可以连续发送请求，不必等待上一条响应，但服务端必须按请求顺序返回响应。因此前一条响应耗时较长时，后续响应仍会发生队头阻塞；管道化没有解决这个问题。

3. 支持缓存处理

响应头的 `Cache-Control: max-age` 和 `Expires` 可分别给出相对和绝对的新鲜度期限，缓存还需要结合响应年龄判断是否可直接复用。

4. 增加 PUT 和 DELETE 方法

5. 支持断点传输

解决上传和下载的中断问题

### HTTP 2.x

1. 二进制分帧

1.x 是基于文本传输的，效率较低，而 2.x 通过二进制将信息分割成小块，提高传输效率。

2. 多路复用

请求数据基于二进制分帧，按小块乱序发送，服务端自行拼凑成完整的数据去处理。

3. 头部压缩

由客户端和服务端共同维护一份头部信息字典，减少头部的重复信息，达到压缩的目的

4. 服务器推送

服务器可以主动向客户端推送资源

## TCP 三次握手和四次挥手

### 三次握手

TCP 建立连接时需要经过三次握手

```
客户端 ------>   SYN    ------> 服务端（我需要请求信息）
客户端 <------ SYN+ACK ------- 服务端（已收到信息，你能不能接收信息）
客户端 ------>   ACK    ------> 服务端（我可以接收信息）
```

三次握手的目的，是为了双方互相确认对方的发送能力和接收能力是正常的，避免浪费资源，为后序的可靠性传输做准备。

### 四次挥手

TCP 连接通常通过双方分别发送 FIN 和确认报文来关闭，下方是常见的四个报文示意

```
客户端 ------> FIN ------> 服务端（我准备断开连接了）
客户端 <------ ACK ------- 服务端（已收到，但是响应数据没发完，等我信号）
客户端 <---- ACK+FIN ----- 服务端（可以断开连接了）
客户端 ------> ACK ------> 服务端（已断开连接）
```

四次挥手的原因是因为服务器需要等报文发送完毕后才能断开。

## HTTPS

### 概念

HTTPS 使用 TLS 保护 HTTP 通信。HTTP/1.1 和 HTTP/2 通常运行在 TCP 上；HTTP/3 则运行在 QUIC 上，不能一概描述为在 TCP 与 HTTP 之间加一层 TLS。

对于基于 TCP 的 HTTPS，建立 TCP 连接后还需完成 TLS 握手，再传输受保护的 HTTP 数据。

HTTP 默认端口为 80，而 HTTPS 默认端口为 443。

常见的公开网站使用受信任的 CA 签发的服务器证书。客户端验证证书链、域名等信息，以确认所连接服务器的身份。

HTTPS 主要缓解了明文 HTTP 的三类风险：

1. 窃听风险

2. 篡改风险

3. 冒充风险

### HTTPS 的特点：

1. TLS 握手通过密钥交换建立共享秘密，并通过证书和数字签名等机制认证服务器；后续应用数据使用派生出的对称密钥进行认证加密。

2. 完整性保护与数字签名

单独把内容摘要和内容一起发送，并不能防止攻击者同时修改两者。TLS 使用带密钥的认证加密保护应用数据，并在握手阶段验证相关消息与服务器身份。

3. 数字证书

服务器在握手中向客户端发送证书链。客户端利用本地信任的根证书验证证书链，同时检查域名和有效期等条件；通常不需要再向 CA 下载一份证书来比较公钥。

### HTTPS 建立连接的过程

前置重要知识点：

1. 公钥与私钥是一对密钥。以 RSA 加密为例，使用接收方公钥加密，由对应私钥解密；数字签名则由私钥生成，并用公钥验证。并非所有非对称算法都提供加密和解密操作。

2. 对称加密使用双方共享的密钥材料。TLS 会从握手建立的共享秘密中派生出不同方向的应用数据密钥。

以常见的 TLS 1.3 证书认证握手为例：

1. 客户端发送 `ClientHello`，提出支持的算法并发送临时密钥交换参数。

2. 服务端返回所选参数和自己的临时密钥交换参数。双方据此计算共享秘密，并派生握手密钥。

3. 服务端发送证书，并用对应私钥对握手内容签名。客户端验证证书链、域名、签名和握手完整性。

4. 双方完成握手后，派生应用数据密钥，使用对称的认证加密保护 HTTP 数据。会话密钥不是由一方直接用证书公钥加密后发送给另一方。
